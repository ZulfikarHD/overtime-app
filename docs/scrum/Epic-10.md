**Lead Area:** Backend (`EarlyWarningService`, `AlertFollowUpService`) + Vue 3 Inertia pages under `resources/js/pages/early-warning/`

---

## Business Context

The client wants overtime consumption problems to be **caught early and acted on**, not just displayed on a chart. Today the dashboard shows a daily "Early Warning" chart with Hijau / Kuning / Merah zones, but nobody is prompted to _do_ anything when a section turns Kuning or Merah.

This epic turns the chart into a complete **alert workflow** with its own sidebar menu:

1. The system **detects** alerts automatically from the daily index (section + day, with a consecutive-day streak).
2. A user opens an alert and sees **why it is happening** (chart + production volume / manpower vitals).
3. The **system writes the 5W2H follow-up itself** (What, Why, When, Where, Who, How, How much) from the alert data (E10-08). The user only **reviews, optionally edits, and sends** it. The client explicitly said the 5W1H is generated by the system, not typed from scratch.
4. The follow-up is **saved as a draft** or **sent by email** to the PIC department ("Who"). A sent follow-up becomes read-only.

The client's HTML draft (`references/Tindak Lanjut Alert — 5W1H (Smartime) (5).html`) is a **content and flow reference only**. It is a single mobile card with static values. The real feature must be a complete, data-driven module in the app's own design system (ISUZU, see `isuzu-frontend-development` skill), not a copy of that HTML.

### Story E10-01: Early Warning Alert Detection Service

**As the** system,  
**I want** to derive alerts automatically from the daily index of every section,  
**So that** users never have to hunt for problems manually.

**Story Points:** 5  
**Priority:** Must Have  
**Status:** 🟢 Done (backend; UI starts in E10-02/E10-03)

#### Definition of an alert

- One alert = **one section on one date** whose daily index is in zone **Kuning** or **Merah** (not Hijau).
- Daily index = the same formula as the Dashboard's Early Warning chart (daily consumption vs. daily pacing target, `CALC-02` applied per day) — **must not diverge** from `getDailyIndexTrend`.
- Zone = `PolicyThresholdService::classifyWith()` using the **section's department** boundaries (department override, else plant default).
- **Severity** = zone of the alert date (Merah > Kuning).
- **Streak (hari berturut-turut)** = number of consecutive **working days** (HKN, from `operational_calendar`) ending on the alert date whose zone is Kuning or Merah. HLR days are skipped and do not break the streak (Q4).
- A section with no configured budget produces **no alert** (not a false Hijau/Merah).

#### Acceptance Criteria

- [x] Service returns alerts for a date range, optionally filtered by department, section, and zone
- [x] Each alert exposes: `section_id`, `section_name`, `department_id`, `department_name`, `alert_date`, `index_pct`, `zone`, `streak_days`, `green_max_pct`, `yellow_max_pct`, `follow_up_status` (`none | draft | sent`), `follow_up_id` (latest)
- [x] Non-admin users only receive alerts of their own department (server-side)
- [x] Hijau days never appear as alerts
- [x] A section's streak resets on a Hijau working day and is unaffected by HLR days
- [x] Sections without a budget are excluded
- [x] Alerts are sorted: Merah first, then Kuning; then by `streak_days` desc, then date desc
- [x] Computing alerts for the whole plant for a 31-day range runs in a **constant number of queries** (no per-section × per-day queries)

#### Technical Tasks

- [x] `php artisan make:class Services/EarlyWarningService` (pragmatic Service pattern, controllers ≤ 30 lines)
- [x] `EarlyWarningService::alertsFor(User $user, Carbon $from, Carbon $to, ?int $departmentId, ?int $sectionId, ?BurnZone $zone): Collection`
- [x] `EarlyWarningService::alertDetail(User $user, Section $section, Carbon $date): array` (single alert + 7-working-day series; reuse `getDailyIndexTrend` semantics)
- [x] Reuse `DashboardKpiService::resolveScoping()` and `PolicyThresholdService`; extract the shared "daily index per section per day" calculation into one method used by **both** the Dashboard chart and this service
- [x] Group by section/day in SQL with `SUM` + `GROUP BY` (MySQL/MariaDB-safe, `whereDate` on date columns; **no SQLite-only syntax**)
- [x] Carbon dates use `Asia/Jakarta`
- [x] Feature tests: zone classification with department override, streak across a weekend, Hijau resets the streak, no-budget section, scope isolation between departments, query count assertion

#### Implementation Notes (delivered)

- `EarlyWarningService::alertsFor()` / `alertDetail()` (+ `isAlert()` helper for E10-06) in `app/Services/EarlyWarningService.php`; shared formula in `DashboardKpiService::calculateDailyIndex()`, `calculateDailyPacing()`, `resolvePlannedHoursForSections()` (also used by `getDailyIndexTrend`).
- Migration `add_alert_date_and_streak_days_to_alert_follow_ups_table` pulled forward from E10-06 (columns + index only; backfill, save/send flow and routes stay in E10-06). Model fillable/casts and factory state `forAlert()` updated.
- Non-admins (Manager and Team Leader) are scoped to their own **department** (not narrowed to a section as the Dashboard does for Team Leaders), matching D3.
- Streak lookback is capped at 60 days before the requested range (constant query count); a working day in a month without budget resets the streak; an HLR alert day counts itself but does not extend the working-day streak.
- Tests: `tests/Feature/EarlyWarningServiceTest.php` (20 tests). Details: [Early Warning Alert Detection](../dev-docs/features/early-warning-alert-detection.md), [ADR-040](../dev-docs/decisions/040-early-warning-alert-detection-shared-daily-index.md).

**So that** the "Why" of the alert is easier to fill in.

**Story Points:** 5  
**Priority:** Should Have

- [ ] Vitals are an **input to the 5W2H generator** (E10-08); this story does not write any "Why" text itself
- [ ] Division by zero (previous value 0) returns `null`, shown as `N/A`, never `Infinity`/`NaN`
- [ ] No fabricated numbers: never default to `+20%` or any dummy

- [ ] `EarlyWarningService::vitalsFor(Section $section, Carbon $date): array` returning `volume_change_pct`, `volume_period_label`, `manpower_change_pct`, `manpower_period_label`

### Story E10-06: 5W2H Follow-Up Linked to an Alert

**As a** Manager or Team Leader,  
**I want** to review the system-generated follow-up of a specific alert, edit it if needed, and save a draft or send it by email,  
**So that** the PIC department is informed and the action is on record.

**Story Points:** 5  
**Priority:** Must Have  
**Status:** 🔴 Not Started

The 5W2H behavior is already implemented at the month level (`AlertFollowUpService`). This story **links it to a concrete alert (section + date)** and moves its UI and routes into the new module.

#### Acceptance Criteria

- [ ] Follow-up belongs to an **alert**: `section_id` + `alert_date` (new columns), plus the existing `department_id`, `fiscal_year`, `fiscal_month`
- [ ] **Zone and index are recomputed server-side** from the alert date at save time (client values ignored); the snapshot is stored (`zone`, `index_pct`, new `streak_days`)
- [ ] A follow-up can only be created for a date that **is an alert** (Kuning/Merah); otherwise 422 with a clear message
- [ ] The form **opens prefilled with the system suggestion** from E10-08 (no empty form); the user can edit every field
- [ ] The saved follow-up keeps a **snapshot of what the system generated** (`generated_payload` JSON + `generated_at`) next to the user's final text, so edits can be shown ("Diubah") and audited
- [ ] Each field shows a small **"Dibuat sistem"** tag, changing to **"Diubah"** when it differs from the snapshot; a **"Reset ke saran sistem"** button restores that field (or all fields) — draft only
- [ ] **Simpan Draft**: requires only **What**; can be re-saved/edited any time while `draft`
- [ ] **Kirim via Email**: requires What, Why, When, Who, How; needs at least one active recipient in the Who department, otherwise a validation error and **nothing is saved/sent** (transaction rolls back)
- [ ] On send: status → `sent`, `sent_by`, `sent_at` set, one queued mail per recipient (`Mail::to($r)->queue(...)`), toast "Follow-up sent by email to the PIC department."
- [ ] A **sent follow-up is read-only** (form disabled, update → 403)
- [ ] At most **one draft per alert** at a time; many sent follow-ups allowed (history). "Follow-up baru" creates a new draft
- [ ] The email contains: section, date, zone, index %, streak, the 5W2H content, how much (Rp and hours), sender, and a link to the alert detail page (Wayfinder URL helper server-side `route('early-warning.show', …)` is acceptable in PHP)
- [ ] Authorization: admin all; others own department only; operators none
- [ ] Rupiah formatting in UI and email (`Rp 7.500.000`), timezone WIB

#### Technical Tasks

- [ ] Migration: add `alert_date` (date, nullable for legacy rows), `streak_days` (unsigned small int, default 0), `generated_payload` (JSON, nullable), `generated_at` (timestamp, nullable); index `(section_id, alert_date)`; backfill legacy rows with `alert_date = created_at date` (migration branches on driver only for DDL if needed)

### Story E10-08: 5W2H Auto-Generator (System-Written Follow-Up)

**As a** Manager or Team Leader,  
**I want** the system to write the What, Why, When, Where, Who, How, and How much of an alert for me,  
**So that** I only review and send instead of analysing the data and typing everything myself.

**Story Points:** 10  
**Priority:** Must Have  
**Status:** 🔴 Not Started  
**Depends on:** E10-01 (alerts + streak), E10-05 (vitals). Consumed by E10-04 / E10-06.

#### Approach: rule-based and explainable

The generator is a **pure PHP service** with no AI model and no external call. It reads the alert plus the data around it, detects likely **causes** using fixed rules, ranks them, and fills the 5W2H from per-cause templates. Same input = same output (deterministic, easy to test). Every generated sentence must contain the number that justifies it ("Kategori Production 78% dari total jam"), so a user can trust or reject it quickly.

#### Field generation

| Field        | How the system fills it                                                                                                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **What**     | Fixed template from the alert: zone, section, index %, how far above the zone limit, streak. Example: "Index harian Assembly 104% (Merah), 14% di atas batas 90%, 3 hari berturut-turut."              |
| **Why**      | Top-ranked cause plus up to 2 supporting causes, each with its evidence number (see cause catalog). Example: "Volume produksi bulan ini +20% sedangkan MP 0%; kategori Production 78% dari total jam." |
| **When**     | Streak start date to alert date, with the number of working days. Example: "24–26 Okt 2026 (3 hari kerja berturut-turut)".                                                                             |
| **Where**    | Department and section name (Q8: no production line in the data).                                                                                                                                      |
| **Who**      | PIC department of the top cause from the admin-editable mapping (Q6); fallback = the alert's own department.                                                                                           |
| **How**      | Action template of the top cause with computed numbers. Example (manpower): "Tambah 5 orang shift malam selama 7 hari kerja."                                                                          |
| **How much** | `suggested_hours` and `suggested_cost_idr` (see formulas below).                                                                                                                                       |

#### Cause catalog (v1)

| Code                     | Detector (all thresholds in `config/early_warning.php`)                                 | Evidence in "Why"                                        | Default PIC (Q6)                | "How" template                                    |
| ------------------------ | --------------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------- | ------------------------------------------------- |
| `MANPOWER_SHORTAGE`      | Volume change ≥ +10% **and** MP change ≤ 0                                              | Volume %, MP %, with their period labels                 | HCM                             | Add N people for D working days                   |
| `CATEGORY_DOMINANT`      | One category (Production / TPM / Project / Others) ≥ 50% of the period's overtime hours | Category name and its share %                            | By category (TPM → maintenance) | Review the category's workload / scheduling       |
| `EMPLOYEE_CONCENTRATION` | Top 3 employees ≥ 40% of the period's hours                                             | Top 3 NPK and their combined share %                     | Own department                  | Redistribute work across more employees           |
| `HOLIDAY_OVERTIME`       | Overtime on HLR days ≥ 30% of the period's hours                                        | HLR share %                                              | Own department                  | Review weekend / holiday scheduling               |
| `UNPLANNED_OVERTIME`     | Actual hours exceed the approved overtime plan (`overtime_plans`) by ≥ 20%              | Plan vs actual hours                                     | Own department / planning       | Align the next overtime plan with the real demand |
| `UNKNOWN`                | No other cause detected                                                                 | "Penyebab belum teridentifikasi dari data yang tersedia" | Own department                  | "Lakukan investigasi penyebab di section ini"     |

Ranking: each detected cause gets a score = the share of excess hours it explains (0–1); the highest score is the **primary** cause (drives Who and How), the next two are **supporting** causes (only appear in Why). Ties are broken by the fixed catalog order above.

#### Formulas for "How much" and the manpower suggestion

- `excess_hours_per_day` = average daily actual hours − daily pacing target, over the streak days (never negative)
- `period_days` = D = default follow-up length (Q9: 7 working days)
- `suggested_hours` = `excess_hours_per_day × D`
- `suggested_headcount` (manpower cause only) = `max(1, ceil(excess_hours_per_day / shift_hours))`, `shift_hours` = 8 (Q9)
- `suggested_cost_idr` = `suggested_hours × average cost per overtime hour of the section` (same cost basis as `CostAnalysisService`, from approved items' `total_cost_snapshot / total_hours` of the last 30 days; fallback = average `effective_hourly_rate` of the section's active employees; if neither exists, return `0` and a note "Estimasi biaya belum tersedia")

#### Acceptance Criteria

- [ ] `EarlyWarningFollowUpGenerator::generate(Section, Carbon $date): array` returns `what`, `why`, `when_date`, `when_text`, `where`, `who_department_id`, `how`, `how_much_hours`, `how_much_cost_idr`, `primary_cause`, `supporting_causes`, and `evidence` (list of cause code + numbers)
- [ ] Output is **deterministic** and **Indonesian or English by user locale** via `__()` keys with placeholders (both `lang/id.json` and `lang/en.json`)
- [ ] Every cause sentence includes its evidence number(s); no sentence is generated without data behind it
- [ ] Causes are detected, scored, and ranked exactly as described; the primary cause drives Who and How
- [ ] **Who** uses the admin mapping (cause → PIC department); a missing or inactive mapping falls back to the alert's own department

## Key Business Rules Implemented in This Epic

| Rule                        | Implementation                                                                                                  |
| --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 3-zone tolerance (D7)       | Hijau ≤ `green_max_pct`, Kuning ≤ `yellow_max_pct`, Merah above — per department, from `PolicyThresholdService` |
| Alert = Kuning or Merah day | `EarlyWarningService::alertsFor()`; Hijau never an alert; sections without budget excluded                      |
| Streak                      | Consecutive HKN working days in Kuning/Merah; HLR skipped                                                       |
| Server-side truth           | Zone/index/streak recomputed on save; client values are display-only                                            |
| Alert, not planning (D5)    | Draft saves; send = queued email only; sent = read-only                                                         |
| Scope isolation             | Non-admins limited to their own department on every route and query                                             |
